## 0. 읽는 법
- 각 항목의 **[프론트]** 표시는 프론트 구현에 직접 영향이 있는 결정이다. **[백엔드]** 는 배경 지식으로만 알면 되고 프론트 코드에 반영할 것이 없다.
- 번호(D1~D12)는 사용자와의 합의 순번이며 `01 부록 A`·`03 §1-3` 과 동일하다. 번호를 재배열하지 않는다.

---

## D1 — 항상 전량 수집 (증분 아님) **[백엔드]**
- `MOD_DATE` 는 `{연도}0101` **고정 하한선**이다. 증분 커서가 **아니다**. 학기 필터는 `TERM_CODE` 로 한다.
- **이유(재논의 방지)**: `MOD_DATE` 는 "해당 일자 이후 수정된 행"을 반환한다. 증분 수집 시 **삭제(폐강)는 `MOD_DATE` 에 흔적을 남기지 않아 감지 불가**하고, 마지막 실행일과 실제 수정일이 어긋나면 변경이 누락된다. 폐강 판정("API 에 없는데 DB 에 있는 것")에는 해당 학기 전량이 필요하다.
- ❌ **"증분 수집으로 바꾸면 효율적"** 류의 제안 금지. 여러 대안 검토 후 사용자가 직접 고른 결정이다.
- 프론트 영향: 없음. 요청 파라미터에 커서·마지막 실행일이 **존재하지 않는다**(`03 §6-1, §6-2`).
- 근거: `01 §4-1`, `03 §1-3`. 사용자 결정.

## D2 — `maxCapacity`·`currentEnrollment` 는 서비스 소유 **[프론트]**
- 두 필드는 학교 API 28개 필드에 **없다**. UPSERT 시 UPDATE 대상에서 제외한다. 신규 생성 시 `maxCapacity` 기본 **40**.
- 프론트 영향: `changedFields[].field` 에 이 두 값이 **절대 나타나지 않는다.** 변경 내용 라벨 매핑 테이블에 넣지 않는다.
- 근거: `03 §8-4`.

## D3 — 폐강 = `status = CLOSED` (물리 삭제 금지) **[프론트]**
- UPSERT 시 API 응답에 없고 DB 에만 있는 과목은 `status = CLOSED` 로 전환한다. **DELETE 하지 않는다**(`Cart`·`Registration` 이 `course_id` 를 FK 참조).
- 프론트 영향: `courses/summary.courseCount` 는 **`CLOSED` 를 포함한 값**이다. "활성 과목 수"로 해석하면 안 된다.
- 근거: `03 §5-1, §10-1`.

## D4 — 적재 전략은 **서버가 판정** (관리자는 대상 학기만 지정) **[프론트]**
- 관리자는 "지금이 upsert 상황인가"를 판단하지 않는다. `courses` 는 항상 단일 학기이므로 대상 학기와 비교하면 전략이 자동 결정된다.
  - 동일 → `UPSERT`(3-way diff, cart·registration **보존**) / 상이 → `REPLACE`(전량 삭제) / DB 비어있음 → `INITIAL`
- ❌ **클라이언트가 전략을 선택·결정하는 UI 를 만들지 않는다.** M2 는 연도·학기 드롭다운뿐이다.
- ⚠️ `POST /sync/jobs` 의 `expectedStrategy` 는 **검증용이지 판정 근거가 아니다.** preflight 응답을 그대로 되돌려 보내 "확인 모달에서 본 것 == 지금 실행될 것"을 대조한다. 불일치 시 서버가 409/`5201`.
- ❌ **"관리자가 전략을 고르게 하자"** 류의 제안 금지. 여러 대안 검토 후 사용자가 직접 고른 결정이다.
- 근거: `01 §1-3, §7-2`, `03 §6-1, §6-2`. 사용자 결정.

## D5 — 업데이트 중 서비스 정상 운영 **[백엔드]**
- Job 실행 중에도 학생 서비스는 계속 동작한다. 점검 모드·서비스 중단이 **없다**. 신청 로직에 `status = ACTIVE` 검증을 추가해 방어한다.
- 프론트 영향: 백오피스에 "점검 모드 전환" UI 가 **없다**.
- 근거: `03 §10-1`.

## D6 — 관리자 계정·토큰은 학생과 분리 **[프론트]**
- `admins` 별도 테이블 + 학생과 분리된 JWT. 학생 인증 흐름(포털 로그인)과 섞지 않는다.
- 토큰 실제 형태는 아래 **기타 확정값** 참조(단일 access 토큰).
- 근거: `03 §2-2, §3-1`.

## D7 — Oracle 직결은 학생 인증 전용 (유지) **[백엔드]**
- `OracleConfig` + `InuMemberRepository`(`F_LOGIN_CHECK` 저장 함수)는 **학생 포털 로그인 인증 전용**이다. 강의 데이터와 무관하며 그대로 유지한다.
- 강의·시간표 데이터는 **INTIP HTTP API**(`https://api.inu.ac.kr/svc/intip/...`)로만 가져온다.
- ❌ 강의 데이터를 Oracle 에서 직접 읽으려는 시도 금지.
- 근거: `03 §1-3`.

## D8 — 과목 정원 수정 화면은 범위 외 **[프론트]**
- `maxCapacity` 를 백오피스에서 편집하는 화면을 **만들지 않는다**(D2 와 별개 결정 — D2 는 동기화 제외, D8 은 UI 부재).
- 화면은 `ADMIN_LOGIN`·`SYNC_MAIN` **2개뿐**이다. 세 번째 화면을 추가하지 않는다.
- 근거: `01 §3`.

## D9 — `courses` 는 항상 단일 학기 → 조회 API 에 학기 필터 미추가 **[백엔드]**
- 기존 `CourseService` 조회에 학년도·학기 필터가 없다. 이는 결함이 아니라 **전제**다. 필터를 추가하지 않는다.
- D4 의 전략 판정이 성립하는 근거이기도 하다.
- 근거: `03 §10-1`.

## D10 — 표시 학기와 데이터 적재는 **완전 독립** **[프론트]**
- `semester_setting`(표시 학기)은 프론트 노출용 라벨일 뿐 `courses` 와 무관하다. 서로를 트리거하지 않는다.
- ⚠️ 카드 1(표시 학기)과 카드 2(적재 학기)의 값이 **달라도 정상**이다. 불일치 경고·동기화 유도 UI 를 **만들지 않는다**.
- ❌ 표시 학기 변경 시 데이터 업데이트를 제안하거나 자동 실행하지 않는다.
- 근거: `01 §1-3, §6-2`, `03 §4`.

## D11 — 미리보기(2단계 적용) 미채택 **[프론트]**
- 확인 모달 이후 **즉시 실행**한다. "변경 사항 미리보기 → 검토 → 적용" 흐름이 없다.
- Job 중간 상태는 `RUNNING` **하나뿐**이다. `PREVIEW`·`PENDING_APPLY` 같은 상태를 만들지 않는다.
- `course_sync_detail.applied` 는 이력 기록용이며 **적용 대기 큐가 아니다**.
- 근거: `01 §8`, `03 §8-3`.

## D12 — enum 미매핑은 경고로 수집 (Job 실패 아님) **[프론트]**
- `CourseCollege`·`CourseDepartment`·`CourseClassification`·`CourseArea`·`CourseType`·`CourseGrade` 의 `fromCode()` 는 미매핑 시 `INVALID_ENUM_TYPE`(8888)을 던진다. **동기화 경로에서만** 이를 우회해 해당 과목을 건너뛰고 `changeType = WARNING` 으로 기록한다.
- Job 은 `SUCCESS` 로 종료될 수 있다. 경고가 있어도 실패가 아니다.
- 프론트 영향: 확장 영역 **경고 탭**(`changeType=WARNING`, 컬럼 = 학수번호·사유). `warningCount > 0` 이어도 상태 배지는 `성공`이다.
- 근거: `01 §6-5`, `03 §10-4`.

## 기타 확정값 (계약에서 고정 — 임의 변경 금지)

### 인증·토큰 (`03 §2-2, §3`)
- 헤더는 **`access-token`**. `Authorization: Bearer` **아님**(기존 `JwtAuthenticationFilter` 와 동일).
- **access 단일 토큰, 만료 2시간. refreshToken 이 존재하지 않는다.** access/refresh 쌍을 전제한 코드(Rotation·화이트리스트·이중 저장)를 만들지 않는다.
- **`POST /auth/logout` 엔드포인트가 없다.** M5 로그아웃은 클라이언트 토큰 폐기 + `/login` 이동만. 서버 호출 없음.
- `/auth/refresh` 는 **만료된 토큰을 헤더로 받아** 재발급한다(기존 `/auth/re-issue` 승계). 401 → refresh 1회 → 실패 시 `/login`.
- 관리자 토큰 식별 = JWT claim `role: "ADMIN"`. 미보유 시 403/`5002`.

### 공통 계약 (`03 §2`)
- 에러 응답 **`{ code: number, message: string }`** — `code` 는 **정수**다(Gravit 의 문자열 도메인 코드 아님). 백오피스 대역 = **5000번대**.
- 목록 페이지 크기 **10행 고정**(서버 고정, 클라 변경 불가). `size` 파라미터 없음.
- 페이지네이션 래퍼 `{ page, totalPages, hasNextPage, content }`, `page` 는 **1부터**.
- datetime 전송 **`"2026-08-05T14:22:00"`** — 오프셋·`Z` **없음**, KST 로컬. 클라이언트에서 UTC 변환하지 않는다.
- Base URL `{API_HOST}/api/v1/admin`.

### 동작 (`01`, `03 §6~7`)
- Job 상태 **`RUNNING` → `SUCCESS` | `FAILED`** 3종 고정.
- 폴링 **2초**, 대상 `GET /sync/jobs/{jobId}`. 진입 시 `courses/summary.runningJobId ≠ null` 이면 폴링 자동 재개.
- 진행률은 **구조화**(`phase`/`current`/`total`). 한글 라벨 매핑은 **클라이언트 책임**. `total = null`(첫 페이지 수신 전)이면 분모 없이 `{단계} 중…` 표기.
- `PERSIST` 단계의 `current`/`total` 단위는 **건수**다(페이지 아님).
- M4 Strict Match 입력값 = **`{연도}-{학기명}`** 정확 일치(예: `2026-여름계절학기`).
- 학기 표시 순서 **1학기 → 여름계절학기 → 2학기 → 겨울계절학기**. ⚠️ `TERM_CODE`(10/20/30/40)로 정렬하면 **틀린다**(여름 30 > 2학기 20).
- 확장 영역 목록 **최초 10건, [더 보기] 10건씩**. 확장은 동시에 1행만.

### 미해결 (실측 후 확정 — 추측 금지)
- `03 §11-1` 의 학교 API 실측 8항목은 **아직 검증되지 않았다.** 결과에 따라 `03` 이 수정될 수 있다.
- 프론트는 실측 결과에 의존하는 값을 **하드코딩하지 않는다**(페이지당 건수, 예상 소요 시간 등).

## 안 되는 것 (요약)
- ❌ D1~D12 를 "더 나은 방식"으로 재제안. 특히 **D1(전량 수집)·D4(서버 판정)** 은 사용자가 대안 검토 후 직접 고른 결정이다.
- ❌ 화면 3개 이상 만들기(D8). ❌ 표시 학기↔적재 학기 불일치 경고(D10). ❌ 미리보기 단계(D11).
- ❌ refresh 토큰·logout 엔드포인트 전제 코드. ❌ 문자열 에러 코드. ❌ UTC 변환. ❌ 페이지 크기 20.
